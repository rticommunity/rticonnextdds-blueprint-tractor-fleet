# RTI Connext DDS Design — Autonomous Tractor Fleet

> **Purpose:** Map the tractor fleet scenario in the [README](../README.md)
> onto RTI Connext DDS 7.7 concepts: domain and domain tag, IDL data types,
> topics and request-reply services, QoS profiles, partitions, content
> filtering, participants, liveliness, and persistence. The normative sources
> are [fleet_types.idl](../fleet_types.idl), [fleet_qos.xml](../fleet_qos.xml),
> and [fleet_persistence.xml](../fleet_persistence.xml).
>
> This document describes what every implementation must do, in any
> language. Language-specific details (classes, threads, API calls) are in
> the component specifications:
> [`tractor_node_spec.md`](../python/spec/tractor_node_spec.md) ·
> [`charging_station_spec.md`](../python/spec/charging_station_spec.md) ·
> [`fleet_ui_spec.md`](../python/spec/fleet_ui_spec.md).
> For installation and launch, see the [Quick Start](../README.md#quick-start).

**Design highlights**

- **Single domain** (ID 0), isolated from other Connext applications by the
  domain tag `tractor-fleet-salinas-CA`
- **Seven topics** for tractor state, telemetry, video, station status, and
  coverage, plus **three request-reply services** for commands and charging
- **One profile per topic and service** in `fleet_qos.xml`, built on Connext
  `BuiltinQosLib` patterns
- **Partitions** for on-demand video, and a **content filter** so each
  tractor receives only the commands addressed to it or to `ALL`
- **Presence from DDS alone:** deadline and liveliness, with no application
  heartbeats; the dashboard, tractors, and stations react to departures
- **Optional RTI Persistence Service** keeps coverage trails across tractor
  restarts
- **`@appendable` types** throughout; no application timestamps (DDS
  `SampleInfo` carries them) and no `request_id` fields (request-reply
  correlates by `SampleIdentity`)

## 1. Domain Architecture

### 1.1 Single Operational Domain

All fleet applications join one DDS domain. The fleet is one cooperating
system: tractors need each other's state, stations serve every tractor, and
the dashboard sees everything, so there is no boundary that would justify a
second domain or Routing Service.

| Domain ID | Name | Purpose |
|---|---|---|
| `0` | **Fleet operations** | All tractor, station, and dashboard data |

Every participant sets the **domain tag** `tractor-fleet-salinas-CA`
(`dds.domain_participant.domain_tag`, propagated, in `ParticipantProfile`).
Participants with different tags never communicate, even on the same domain
ID, so the fleet stays isolated from unrelated Connext applications. The
`DOMAIN_ID` and `DOMAIN_TAG` environment variables override both values (the
launch scripts pass them through, and the smoke test uses a private tag). Both
`fleet_qos.xml` and `fleet_persistence.xml` expand `$(DOMAIN_TAG)` with the
same default in `<configuration_variables>`, so applications started directly
still get the default tag, and Persistence Service always follows the fleet.

Monitoring Library 2.0 (enabled by default; `RTI_MONITORING2_ENABLE=FALSE`
disables it) publishes its telemetry from its own participant on a separate
observability domain; it is not part of the fleet's data.

### 1.2 Partitions

The fleet uses partitions for one purpose: matching the dashboard's video
reader with exactly one tractor's video writer (§9). All other entities use
the default partition.

## 2. IDL Data Types

All types are defined in [fleet_types.idl](../fleet_types.idl), the single
source of truth. Generated type support is checked in for Python
([python/fleet_types.py](../python/fleet_types.py), regenerated by
[python/types_generate.sh](../python/types_generate.sh) after an IDL change).

### IDL Conventions

| Convention | Rule |
|---|---|
| Extensibility | Every enum and struct is `@appendable` |
| Keys | Stateful topic types are keyed by `tractor_id` or `station_id` (`@key string<64>`); request and reply types are unkeyed |
| Bounds | Strings `string<64>` (descriptions `string<256>`); waypoint sequences up to 64; station queue up to 16; video frames up to 1,000,000 octets |
| Timestamps | None in the types; readers use `SampleInfo` source and reception timestamps |
| Correlation | No `request_id` fields; request-reply correlates by DDS `SampleIdentity` |
| Optional members | Command parameters are `@optional` typed structs, not JSON strings |

### Type Categories

| Category | Types |
|---|---|
| Enums | `TractorStatus` (`UNKNOWN`, `MOVING`, `IDLE`, `HOLDING`, `CHARGING`), `TractorIntentType` (`UNKNOWN`, `FOLLOW_PATH`, `GOTO`, `IDLE`, `CHARGE_QUEUE`, `CHARGE_DOCK`), `Command` (`UNKNOWN`, `STOP`, `FOLLOW_PATH`, `GOTO`, `RESUME`, `SET_PATH`, `CHARGE`) |
| Helper structs | `Position`, `Velocity3`, `Waypoint`, `QueueEntry` |
| Topic types | `KinematicState`, `OperationalState`, `Intent`, `Telemetry`, `VideoFrame`, `StationStatus`, `CoveragePoint` |
| Command service | `GotoParameters`, `SetPathParameters`, `CommandRequest`, `CommandResponse` |
| Charging services | `SlotReserve`, `SlotAssignment`, `SlotRelease`, `SlotReleaseAck` |

| Topic type | Key | Fields |
|---|---|---|
| `KinematicState` | `tractor_id` | `position`, `velocity`, `heading` |
| `OperationalState` | `tractor_id` | `status`, `battery_level` |
| `Intent` | `tractor_id` | `intent_type`, `target_position`, `path_waypoints`, `path_index` |
| `Telemetry` | `tractor_id` | `cpu_usage`, `memory_usage`, `temperature`, `signal_strength` |
| `VideoFrame` | `tractor_id` | `frame_data` (JPEG) |
| `StationStatus` | `station_id` | `dock_x`, `dock_y`, `is_occupied`, `docked_tractor_id`, `queue` of `QueueEntry` (`tractor_id`, zero-based `rank`, `confirmed`, always true) |
| `CoveragePoint` | `tractor_id` | `x`, `y` |

| Request → reply | Request fields | Reply fields |
|---|---|---|
| `CommandRequest` → `CommandResponse` | `tractor_id` (or `ALL`), `command`, optional `goto_params` (`x`, `y`, `speed`; zero speed keeps the current speed), optional `set_path_params` (`waypoints`) | `tractor_id`, `success`, `description`, `resulting_status`, `resulting_intent` |
| `SlotReserve` → `SlotAssignment` | `tractor_id`, `station_id`, `battery_level` | `station_id`, `slot_id`, `granted`, `queue_rank`, `dock_x`, `dock_y` |
| `SlotRelease` → `SlotReleaseAck` | `tractor_id`, `slot_id`, `station_id` | `station_id`, `slot_id`, `success` |

`ALL` is a reserved tractor ID: it addresses every tractor (§7), and no
tractor may use it as its own ID.

## 3. Topics

Each topic has the same name as its type, except `LiveVideo`, whose type is
`VideoFrame`: the topic names the flow, the type names one sample.

| Topic Name | IDL Type | Key | Pattern | QoS Profile |
|---|---|---|---|---|
| `KinematicState` | `KinematicState` | `tractor_id` | Pub/Sub (periodic, 10 Hz) | `KinematicStateProfile` |
| `OperationalState` | `OperationalState` | `tractor_id` | Pub/Sub (state, on change) | `OperationalStateProfile` |
| `Intent` | `Intent` | `tractor_id` | Pub/Sub (state, on change) | `IntentProfile` |
| `Telemetry` | `Telemetry` | `tractor_id` | Pub/Sub (periodic, 1 Hz) | `TelemetryProfile` |
| `LiveVideo` | `VideoFrame` | `tractor_id` | Pub/Sub (streaming, ~5 fps, on demand) | `VideoProfile` |
| `StationStatus` | `StationStatus` | `station_id` | Pub/Sub (state, on change) | `StationStatusProfile` |
| `CoveragePoint` | `CoveragePoint` | `tractor_id` | Pub/Sub (history, persistent) | `CoverageProfile` |

Producers write state topics only when tracked values change:
`OperationalState` when the status or the battery level rounded to 0.1
changes; `Intent` when the intent, rounded target, path index, or path
changes; `StationStatus` once at startup and after every reservation, release,
or departure handled. Tractors check for changes at 10 Hz.

### Request/Reply Services

| Service Name | Request Type | Reply Type | QoS Profile | Repliers | Requesters |
|---|---|---|---|---|---|
| `TractorCommand` | `CommandRequest` | `CommandResponse` | `CommandProfile` | Every tractor (content-filtered, §5) | Fleet UI |
| `ChargingSlotReserve` | `SlotReserve` | `SlotAssignment` | `SlotNegotiationProfile` | Every station | Tractors |
| `ChargingSlotRelease` | `SlotRelease` | `SlotReleaseAck` | `SlotNegotiationProfile` | Every station | Tractors |

All repliers of a service share its name, so a request reaches every replier
of that service unless a content filter narrows it. The request topic of a
service is named `<service>Request` (for example `TractorCommandRequest`),
the default naming of Connext request-reply.

## 4. QoS Profiles

All profiles are in [`fleet_qos.xml`](../fleet_qos.xml), library
`FleetQosLibrary`. Each inherits from a Connext built-in pattern and overrides
only what the fleet needs. Every DataWriter, DataReader, `Requester`, and
`Replier` is created with its profile's QoS, so all endpoint QoS is tuned in
that one file.

| Profile | Inherits From | Used By | Key Policies and Overrides |
|---|---|---|---|
| `ParticipantProfile` | `BuiltinQosLib::Generic.Common` | Every participant | Domain tag (§1.1); discovery and reliability snippets; `SPDP \| SEDP`; UDPv4 only (§12) |
| `KinematicStateProfile` | `BuiltinQosLib::Pattern.PeriodicData` | `KinematicState` | Best-effort, volatile, keep-last 1; deadline 200 ms writer / 500 ms reader; automatic liveliness, 30 s lease; reader multicast `239.255.1.1` |
| `OperationalStateProfile` | `BuiltinQosLib::Pattern.Status` | `OperationalState` | Reliable, transient-local, keep-last 1; automatic liveliness, 30 s lease; reader multicast `239.255.1.2` |
| `IntentProfile` | `BuiltinQosLib::Pattern.LastValueCache` | `Intent` | Reliable, transient-local, keep-last 1; automatic liveliness, 30 s lease; reader multicast `239.255.1.3` |
| `TelemetryProfile` | `BuiltinQosLib::Pattern.Streaming` | `Telemetry` | Best-effort, volatile; deadline 2 s writer / 5 s reader |
| `VideoProfile` | `BuiltinQosLib::Pattern.Streaming` | `LiveVideo` | Best-effort, volatile; deadline 1 s writer / 2 s reader |
| `StationStatusProfile` | `BuiltinQosLib::Pattern.Status` | `StationStatus` | Reliable, transient-local, keep-last 1 |
| `CoverageProfile` | `BuiltinQosLib::Pattern.Status` | `CoveragePoint` | Reliable, **persistent**, keep-last 1000; `max_samples` 10000, `max_samples_per_instance` 2000 (writer and reader) |
| `CommandProfile` | `BuiltinQosLib::Pattern.RPC` | `TractorCommand` | Reliable, keep-all, heartbeat and NACK timing tuned for request-reply |
| `SlotNegotiationProfile` | `BuiltinQosLib::Pattern.RPC` | `ChargingSlotReserve`, `ChargingSlotRelease` | Same as `CommandProfile` |

Separate topics with their own QoS keep flows independent: best-effort video
and kinematics never delay reliable state, so there is no head-of-line
blocking between them.

## 5. Content-Filtered Topics

| Reader | Topic | Filter | Parameters | Effect |
|---|---|---|---|---|
| Each tractor's `TractorCommand` replier | `TractorCommandRequest` | `tractor_id = %0 OR tractor_id = %1` | `'<own tractor_id>'`, `'ALL'` | The tractor receives only commands for itself or for the whole fleet |

The replier is created on a `ContentFilteredTopic` of the service's request
topic. Connext evaluates the filter at the writer, so a command for one
tractor is sent only to that tractor; the others never receive it and never
reply. A request to an unknown tractor ID passes no filter and gets no reply.

The filter is a per-tractor choice. A tractor without it still interoperates:
it receives every command, ignores those for other tractors, and replies
"not addressed to me", which requesters ignore. Implementations should keep
the ID check in the handler as a safeguard even with the filter.

**Partitions or filters.** Video uses a partition instead (§9): the
dashboard's interest changes at runtime with the operator's selection, and a
partition change unmatches the other writers completely, which tells each
tractor to stop rendering. Commands use a filter: the replier's interest is
fixed for its lifetime, and the filter is expressed on the data itself.

## 6. DDS Participants and Data Flows

### Publish/Subscribe Matrix

| Topic / Service | Tractor | Charging Station | Fleet UI | Persistence Service |
|---|---|---|---|---|
| `KinematicState` | **P/S** | | S | |
| `OperationalState` | **P/S** | S (presence only) | S | |
| `Intent` | **P/S** | | S | |
| `Telemetry` | **P** | | S | |
| `LiveVideo` | **P** (partition = own ID) | | S (partition = selected tractor) | |
| `StationStatus` | S | **P** | S | |
| `CoveragePoint` | **P** | | S | **S/P** (stores, replays) |
| `TractorCommand` | **rep** (filtered) | | req | |
| `ChargingSlotReserve` | req | **rep** | | |
| `ChargingSlotRelease` | req | **rep** | | |

**P** = publish, **S** = subscribe, **P/S** = both, **req** = requester,
**rep** = replier. Each process has one participant and one reader per topic
it reads, however many tractors or stations there are.

### 6.1 Tractor Participant

Each tractor runs one participant, named with its `tractor_id`, role
`Tractor`.

| Direction | Topic / Service | Notes |
|---|---|---|
| **Publish** | `KinematicState` | 10 Hz |
| **Publish** | `OperationalState`, `Intent` | On change |
| **Publish** | `Telemetry` | 1 Hz, simulated CPU, memory, temperature, link quality |
| **Publish** | `LiveVideo` | Own Publisher, partition = `tractor_id`; renders only while matched (§9) |
| **Publish** | `CoveragePoint` | During path work, at least one arena unit apart (§10) |
| **Subscribe** | `KinematicState`, `OperationalState`, `Intent` | Peers' state for collision avoidance and rendering; own samples ignored |
| **Subscribe** | `StationStatus` | Station positions and queues for station choice and queue progress (§8) |
| **Replier (filtered)** | `TractorCommand` | §5, §7 |
| **Requester** | `ChargingSlotReserve`, `ChargingSlotRelease` | §8 |

### 6.2 Charging Station Participant

Each station runs one participant, named with its `station_id`, role
`ChargingStation`, and manages one dock with a FIFO queue kept in memory.

| Direction | Topic / Service | Notes |
|---|---|---|
| **Publish** | `StationStatus` | Dock position, occupancy, docked tractor, queue |
| **Subscribe** | `OperationalState` | Data unused; instance states detect departed tractors (§11) |
| **Replier** | `ChargingSlotReserve`, `ChargingSlotRelease` | §8 |

### 6.3 Fleet UI Participant

One participant, named and role-named `FleetUI`. It serves the browser
dashboard; HTTP, Server-Sent Events, and MJPEG exist only between the
browser and this process.

| Direction | Topic / Service | Notes |
|---|---|---|
| **Subscribe** | All seven topics | `LiveVideo` on its own Subscriber whose partition is the selected tractor (initially `__NONE__`, which matches nothing) |
| **Requester** | `TractorCommand` | One tractor, or `ALL` (§7) |

## 7. Request/Reply: Commands

Every tractor replies on `TractorCommand`; the request's `tractor_id` names
the target, or `ALL`.

- **One tractor.** The requester sends one request and waits up to five
  seconds for the reply whose `tractor_id` is the target. Thanks to the
  filter (§5) only the target replies.
- **Whole fleet.** The requester sends **one** request with
  `tractor_id = "ALL"`. Every tractor receives it at about the same moment,
  acts on it, and replies; the requester collects the correlated replies
  until every tractor it knows has answered or five seconds pass, and reports
  which tractors acknowledged. A fleet-wide STOP is one write, with no list of
  addresses and no connection per tractor, and tractors the requester hasn't
  seen yet are included.

| Command | Effect on the tractor |
|---|---|
| `CMD_STOP` | Saves the current status, sets `STATUS_IDLE`, zeros horizontal velocity |
| `CMD_FOLLOW_PATH` | Aborts any held charge slot, resumes the loop path, sets moving, resets coverage arming, applies a positive speed if given |
| `CMD_GOTO` | Aborts any held charge slot, moves to the target at an optional positive speed, then holds there; missing parameters mean the current position |
| `CMD_RESUME` | Applies a positive speed if given; restores the pre-stop status, or resumes according to the current intent |
| `CMD_SET_PATH` | Replaces the loop route if at least two waypoints are given, otherwise fails; does not change the intent |
| `CMD_CHARGE` | Rejected if already charging or requested; otherwise starts station selection and reservation (§8) |

A tractor starts at a random arena position with battery 100 %, speed 2.0,
`STATUS_MOVING`, and `INTENT_FOLLOW_PATH` on a random loop of 5–8 waypoints.

## 8. Charging Workflow

Charging combines shared state (`StationStatus`) with directed requests.

1. Charging starts after `CMD_CHARGE` or automatically below 20 % battery.
2. The tractor picks a station from its cache of `StationStatus` samples:
   shortest queue first, then nearest dock. With no station known, it
   abandons the attempt and stays on task.
3. It sends one `SlotReserve` naming that `station_id` and waits up to five
   seconds for a granted `SlotAssignment` from it. Every station receives the
   request; the others answer `granted=false` without touching their queues.
4. The chosen station appends the tractor to its FIFO with a new
   eight-character `slot_id` and publishes `StationStatus`.
5. Rank 0 sets `INTENT_CHARGE_DOCK` and the tractor drives to the dock. A
   positive rank sets `INTENT_CHARGE_QUEUE` and a waiting position 10 + 8 ×
   rank units from the dock, toward the arena center.
6. From then on, queue progress comes from published `StationStatus`
   samples, with no polling: reaching rank 0 sends the tractor to the dock,
   another rank moves its waiting position, and disappearing from the queue
   while waiting aborts the charge.
7. At the dock the tractor enters `STATUS_CHARGING`, gains 2 % per second,
   and releases at 95 %.
8. Completion, cancellation, or a conflicting movement command sends
   `SlotRelease`. The station removes the slot, promotes the next tractor,
   publishes `StationStatus`, and replies `SlotReleaseAck`.

The tractor sends releases without waiting for the acknowledgement. Release
handling is idempotent: an unknown or already-removed slot returns success.
Reservations have no timer; a station also frees the slots of a tractor that
leaves the system (§11). Queues are in memory and are lost when a station
restarts.

## 9. Demand-Driven Video

Video selection uses the Partition QoS:

1. Each tractor creates its `LiveVideo` writer on its own Publisher whose
   partition is the tractor's ID.
2. The dashboard's video reader is on its own Subscriber, initially in the
   partition `__NONE__`, which no writer uses, so no video matches.
3. Selecting a tractor changes the Subscriber's partition to that tractor's
   ID: the previous writer unmatches and the selected one matches.
4. Each tractor renders and writes JPEG frames (400 × 300, about 5 fps) only
   while its video writer has a matched reader.
5. Stopping video restores `__NONE__`, so every video writer is unmatched.

Starting and stopping video needs no application protocol: it is a QoS change
on the dashboard, and tractors that nobody watches spend no CPU on rendering.

## 10. Coverage and Persistence

`CoveragePoint` uses `CoverageProfile`: persistent durability with up to 1000
samples per tractor in the writer and reader history. A tractor publishes a
point only while all of these hold:

- it is moving with `INTENT_FOLLOW_PATH`;
- it has reached a waypoint since coverage was last reset;
- no charge request is in progress; and
- it is at least one arena unit from the last point it published.

Coverage resets when follow-path restarts, when a charge attempt starts, and
when charging ends, so travel to, at, and from a station adds no coverage.

### Persistence Service

Persistence Service is optional. Without it, each tractor's writer still
keeps its last 1000 points and delivers them to late-joining readers, so a
restarted dashboard redraws every trail; a restarted tractor's earlier trail
is lost with its writer. With it, the service stores the samples and replays
them after tractor restarts as well. Clearing coverage on the dashboard is
local to the dashboard; it does not dispose instances or delete stored data.

[fleet_persistence.xml](../fleet_persistence.xml) defines service
`tractorFleetDisk`:

| Setting | Value |
|---|---|
| Participant | `tractorFleetPersistenceParticipant`, domain tag `$(DOMAIN_TAG)` |
| Storage | Filesystem directory `$(STORAGE_DIRECTORY)`, file prefix `tractorFleetDisk_` |
| Topics | Persistence group filter `*` (every persistent topic: `CoveragePoint`) |
| Entities | One shared publisher and subscriber, `SystemPersistenceQosLib::QosProfile` |
| Domain | `0` in the XML; `demo_start.sh` passes `-domainId` with the selected domain |

In the demo, `STORAGE_DIRECTORY` is `persistent_data/` at the repository root
(`PERSISTENCE_STORAGE_DIR` overrides it; the smoke test uses a temporary
directory).

## 11. Fault Tolerance and Liveliness

| Mechanism | DDS Feature | Application |
|---|---|---|
| **Position updates stopped** | Deadline QoS (500 ms on the `KinematicState` reader) | The dashboard marks the tractor *stale* ("no update for N s") until its next sample |
| **Tractor departed** | Automatic liveliness (30 s lease) and writer deletion; reader instance state `NOT_ALIVE_NO_WRITERS` | The dashboard marks it *offline* and removes it 10 s later; tractors stop avoiding it; stations free its slots |
| **Late-join state recovery** | `TRANSIENT_LOCAL` on `OperationalState`, `Intent`, `StationStatus` | New participants get current state from live writers |
| **Coverage history** | `PERSISTENT` on `CoveragePoint`; optional Persistence Service | Late joiners get recent trails; with the service, trails survive tractor restarts |
| **Lost samples** | `RELIABLE` on state, coverage, and request-reply; `BEST_EFFORT` on periodic flows | Reliable data is repaired after a link drop; periodic samples are superseded by the next one |
| **Address changes** | Participant identity independent of network address | After roaming or reconnecting, discovery re-announces and peers match again |

### Presence

Applications learn about presence from DDS alone; there is no application
heartbeat or timeout code.

- **Writer gone.** When a tractor's writers disappear, readers receive a
  sample without data whose instance state is `NOT_ALIVE_NO_WRITERS`: at once
  after an orderly shutdown, which deletes the writers, or when the 30-second
  liveliness lease expires after a crash (about 30–50 s in practice,
  depending on when the middleware checks the lease). Applications map the
  instance to its `tractor_id` from earlier valid samples. Tractors drop the
  peer from collision avoidance (its `KinematicState` instance); the
  dashboard marks it offline (`KinematicState`); stations free its slots,
  promote the next tractor, and publish `StationStatus` (`OperationalState`).
- **Updates stopped.** A missed `KinematicState` deadline marks a tractor
  stale on the dashboard; the next sample makes it live again. The deadline
  fires repeatedly while a tractor is silent, so every silent tractor is
  reported within a few periods.
- **Why topic instances, not participant discovery.** Stations use
  `OperationalState` rather than built-in participant discovery: the
  tractor's identity then comes from the IDL key, not from a
  participant-naming convention, and nothing assumes one tractor per
  participant.

Deadline misses on other topics are not acted on.

### Failure and Recovery

| Condition | Behavior |
|---|---|
| Orderly shutdown | Ctrl-C and SIGTERM (sent by `scripts/demo_stop.sh`) take the same path in every application: close the request-reply objects, close the participant, finalize the participant factory. Peers learn of the departure immediately. With Monitoring Library 2.0 enabled, finalization takes several seconds, so `demo_stop.sh` waits up to `GRACE_SECONDS` (default 10) before force-killing |
| Tractor crash | Stale within about a second; offline, dropped from avoidance, and its slots freed after the lease |
| Station loss | Not handled at the application level; tractors keep its last `StationStatus`, and its queue is lost |
| Reservation timeout | After five seconds without a granted assignment from the chosen station, the tractor abandons the attempt and stays on task |
| Release reply lost | No effect: the tractor doesn't wait for it, and releases are idempotent |
| Link down longer than the lease | Peers treat the tractor as departed; a station frees its slot. When it returns, it is rediscovered; a queued tractor that finds itself missing from the queue aborts its charge, and a docked one finishes and sends a release the station treats as done |

## 12. Discovery Configuration

| Setting | Value | Notes |
|---|---|---|
| **Discovery plugins** | `SPDP \| SEDP` | Simple participant and endpoint discovery, for interoperability with older versions and other vendors (SPDP2 is more efficient but must be enabled explicitly) |
| **Transport** | UDPv4 only | Shared memory disabled, so all traffic uses the network stack, as in a multi-host deployment |
| **Initial peers** | Connext defaults | Multicast discovery on the LAN; a unicast peer list or Discovery Service would be needed across networks |
| **Optimizations** | `Optimization.Discovery.Endpoint.Fast`, `Optimization.ReliabilityProtocol.Common` | Faster endpoint discovery and reliability tuning |
| **State multicast** | Reader receive addresses `239.255.1.1`–`.3` | `KinematicState`, `OperationalState`, and `Intent` samples are sent once to a group instead of once per reader |

```xml
<qos_profile name="ParticipantProfile" base_name="BuiltinQosLib::Generic.Common">
    <domain_participant_qos>
        <base_name>
            <element>BuiltinQosSnippetLib::Optimization.Discovery.Endpoint.Fast</element>
            <element>BuiltinQosSnippetLib::Optimization.ReliabilityProtocol.Common</element>
        </base_name>
        <!-- property: dds.domain_participant.domain_tag = $(DOMAIN_TAG), propagated -->
        <discovery_config>
            <builtin_discovery_plugins>SPDP | SEDP</builtin_discovery_plugins>
        </discovery_config>
        <transport_builtin><mask>UDPv4</mask></transport_builtin>
    </domain_participant_qos>
</qos_profile>
```

### Launch Defaults

[shared/fleet_common.sh](../shared/fleet_common.sh) holds the defaults shared
by every launcher; [scripts/demo_start.sh](../scripts/demo_start.sh) starts
the processes.

| Setting | Default |
|---|---|
| Domain ID / domain tag | `0` / `tractor-fleet-salinas-CA` (`DOMAIN_ID`, `DOMAIN_TAG` override) |
| Tractors | `tractor1` … `tractor5` |
| Stations | `station1` at (8, 92); `station2` at (92, 8) |
| Arena | Coordinates clamped to 0–100 on each axis |
| Dashboard | `http://localhost:5000` |
| Persistence Service | `DEMO_RUN_PERSISTENCE_SERVICE`: `AUTO` (default; start it if `$NDDSHOME/bin/rtipersistenceservice` exists), `FORCED_ON`, `FORCED_OFF` |
| License | `RTI_LICENSE_FILE`; with `NDDSHOME` set it defaults to `$NDDSHOME/rti_license.dat` |

`demo_start.sh` accepts `all` (default), `tractors`, `stations`, `ui`,
`persistence`, `tractor <name>`, and `station <name>`. In `all` mode it starts
Persistence Service (if selected), then the stations, then the tractors at
two-second intervals, and runs the dashboard in the foreground.

## 16. Architecture-to-DDS Mapping Summary

| Requirement (README) | DDS Realization |
|---|---|
| Dynamic discovery, no configured addresses | SPDP/SEDP; participants identified independently of network address |
| Late-joiner convergence | `TRANSIENT_LOCAL` state topics; `PERSISTENT` coverage |
| Presence detection without heartbeats | Automatic liveliness (30 s) and deadline (500 ms); reader instance states |
| Mixed connectivity | `RELIABLE` repair for state and commands; `BEST_EFFORT` periodic flows superseded by the next sample |
| Per-flow QoS | One profile per topic and service in `fleet_qos.xml` |
| Scale (5 to 100+ tractors) | One reader per topic per process; multicast for the shared state topics |
| Commands to one tractor or all | Shared service, `tractor_id` or `ALL`, content filter per tractor |
| Video on demand | Partition per tractor; render only while matched |
| Fleet isolation | Domain tag |
| Coverage history across restarts | Persistent durability; RTI Persistence Service |
